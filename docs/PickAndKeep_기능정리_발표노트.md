## 1. 구현된 기능 상세

각 기능은 **무엇을 / 왜 / 발표용 한 줄** 순서로 정리한다.

### 1-1. S3 비공개 저장 + 임시 링크 (Presigned URL)
- **무엇을**: 사진은 퍼블릭 액세스가 차단된 S3 버킷에 저장하고, 화면에 보여줄 때만 1시간짜리 임시 링크를 만든다.
- **왜**: 개인 사진이라 버킷을 공개하면 주소만 알면 누구나 볼 수 있다. 임시 링크는 시간이 지나면 자동으로 막힌다.
- **발표용**: "버킷은 완전히 잠가 두고, 사진을 볼 때만 1시간 동안 유효한 출입증을 발급합니다."
- 함수: `upload_photo`, `get_photo_url`, `delete_photo`

### 1-2. S3 파일 이름 규칙
- **무엇을**: `hold/2026/11/<무작위 12자>_<영문 이름>.jpg` 형태로 저장한다. 원래 이름(한글 포함)은 DB에 따로 저장한다.
- **왜**: 한글이나 공백이 들어간 이름은 URL에서 깨지기 쉽다. 같은 이름의 사진이 덮어써지는 것도 무작위 문자열로 막는다.
- **발표용**: "S3에는 겹치지 않는 영문 이름으로 저장하고, 사용자가 보는 원래 이름은 DB가 기억합니다."

### 1-3. 안전한 보관함 이동 (보류함 → 평생 보관함)
- **무엇을**: 복사 → DB 수정 → 원본 삭제 순서로 옮긴다. DB 수정이 실패하면 복사본을 지운다.
- **왜**: S3에는 "이동" 기능이 없어서 복사와 삭제로 처리해야 한다. 중간에 실패해도 S3와 DB가 서로 다른 위치를 가리키지 않게 하려는 것이다.
- **발표용**: "중간에 오류가 나도 사진이 사라지거나 기록이 꼬이지 않도록 순서를 설계했습니다."
- 함수: `move_photo`

### 1-4. 사진 기록 DB (SQLite)
- **무엇을**: 사진마다 원래 이름, S3 위치, 보관함, AI 라벨, 크기, 업로드 시각, 마지막 열람 시각을 기록한다.
- **설계 포인트**
  - 시각은 전부 UTC 기준 ISO 형식으로 저장해, 문자열 비교만으로 "60일 지났는지"를 판단한다.
  - WAL 모드를 켜서 여러 프로세스가 동시에 써도 잠금 오류가 덜 나게 했다.
  - 잘못된 보관함 이름(keep/hold 외)은 DB 규칙(CHECK)과 코드 양쪽에서 막는다.
- **발표용**: "서버 한 대 규모라 별도 DB 서버 없이 파일 하나로 동작하는 SQLite를 썼습니다."
- 함수: `init_db`, `save_photo_record`, `get_photos`, `get_photo`(번호로 하나 찾기), `delete_photo_record`, `update_category`
- **그룹(카테고리) 저장 (11/24)**: AI가 나눈 그룹을 사용자가 분류 화면에서 바꿀 수 있고, 그 **최종 그룹**을 `category` 열에 저장한다. 보관함을 그룹별로 보여 줄 수 있고, 저장한 뒤에도 `update_category(id, 그룹)`로 바꿀 수 있다. DB에는 화면 이름("음식") 대신 key(`food`)를 저장해 이름을 바꿔도 DB는 그대로다
- **DB 구조가 바뀌어도 데이터 유지**: 새 열(`file_hash`, `notified_at`, `category`)은 `init_db()`가 기존 DB 파일에 자동으로 추가한다. 서버 DB를 지우지 않고 기능을 늘릴 수 있다
- **사진 번호(id)로 주고받기**: 사진을 평생 보관함으로 옮기면 S3 위치(`s3_key`)는 바뀌지만 번호는 그대로라, 화면끼리는 번호를 넘긴다. 번호로 찾으면 DB에 기록된 사진만 열 수 있다는 장점도 있다

### 1-5. 중복 사진 저장 방지
- **무엇을**: 사진 원본(HEIC 변환 전)의 SHA-256 지문(해시)을 저장하고, 같은 지문이 이미 있으면 저장하지 않는다.
- **왜**: 웹 서비스라 폰 사진을 자동으로 지울 수 없다. 사용자가 백업 후 폰에서 안 지우고 다시 올리면 같은 사진이 두 번 저장된다. 그러면 S3 비용이 늘고, 보관함이 중복되고, 확보 용량이 부풀려진다.
- **방법**: B가 Rekognition 캐시용으로 이미 계산하는 해시를 재사용한다(추가 비용 없음). DB에는 중복 방지 인덱스를 둔다.
- **한계**: 파일 내용이 완전히 같을 때만 잡는다. 카톡 재압축본이나 편집본은 다른 사진으로 본다.
- **발표용**: "사진의 지문을 비교해서, 이미 백업한 사진은 다시 저장하지 않습니다."
- 함수: `is_duplicate`, `save_photo_record(..., file_hash=)`

### 1-6. 열람 기록은 사진을 눌렀을 때만
- **무엇을**: 보관함 목록에 썸네일로 보이는 것은 열람으로 치지 않고, 사진을 눌러 크게 볼 때만 "마지막 열람 시각"을 갱신한다.
- **왜**: 목록만 열어도 열람으로 치면, 보류함을 한 번 열 때마다 모든 사진의 60일 타이머가 초기화된다. 그러면 알림이 사실상 울리지 않는다.
- **발표용**: "보류함 목록을 훑어본 것과 사진을 실제로 다시 본 것을 구분해서 기록합니다."
- 함수: `get_photo_url(key, mark_viewed=False)` (목록용) / `get_photo_url(key)` (크게 보기용)

### 1-7. 확보 용량 계산
- **무엇을**: 저장된 사진의 **원본 크기** 합계를 보여준다. 폰에서 지우면 그만큼 공간이 생긴다는 뜻이다.
- **포인트**: S3에는 변환된 JPG가 올라가지만, 폰에서 실제로 확보되는 건 원본 크기라서 원본 크기를 기록한다.
- 함수: `get_saved_size`

### 1-8. 코드에 비밀 정보 없음
- **무엇을**: 버킷 이름 같은 설정은 `.env`에서 읽고, AWS 키는 코드에 전혀 없다. 로컬에서는 자격 증명 파일을, EC2에서는 IAM 역할(`LabInstanceProfile`)을 쓴다.
- **왜**: 저장소가 Public이라 키가 올라가면 바로 악용될 수 있다.
- **발표용**: "서버는 키 없이 IAM 역할로 AWS에 접근하고, 설정값은 환경 파일로 분리했습니다."

### 1-9. 자동 테스트
- `python3 test_a_infra.py`: DB 11단계와 S3 5단계, 총 16단계를 확인한다. 테스트 전용 DB를 쓰고, 끝나면 S3 테스트 사진까지 지운다.
- `python3 test_a_infra.py --db-only`: AWS 없이 DB만 확인한다.

### 1-10. EC2 서버 (키 없이 IAM 역할로 S3 접근)
- **구성**: Ubuntu 24.04 LTS, t3.small(2 vCPU, 2GiB), 디스크 20GiB gp3, us-east-1
- **보안 그룹 `pick-and-keep-sg`**: HTTP(80)는 누구나(웹사이트 입구), SSH(22)는 A의 IP만(서버 관리 출입문)
- **IAM 역할**: 인스턴스에 `LabInstanceProfile`(LabRole)을 붙여, 서버에는 AWS 키 파일이 전혀 없다. 서버 `.env`에는 버킷 이름 같은 설정만 있다
- **세팅 순서**: SSH 접속 → `python3-venv` 설치 → GitHub에서 `git clone` → venv + `pip install` → `.env` 작성 → `test_a_infra.py` 실행
- **검증**: 서버에서 테스트 11단계 전부 통과 (11/22) → 키 없이 역할만으로 S3 업로드·임시 링크·이동·삭제 동작 확인
- **발표용**: "서버에는 AWS 비밀 키가 한 줄도 없습니다. EC2에 IAM 역할을 붙여서, AWS가 서버에 임시 권한을 자동으로 발급해 줍니다."
- **관리 도구** `deploy/check_access.py`: 지금 서버 주소, 내 노트북 주소, SSH 허용 여부를 한 번에 보여 주고, `--fix`로 SSH 허용 주소를 지금 노트북 주소로 바꾼다 (HTTP 규칙은 건드리지 않음)

### 1-11. 보류함 알림 메일 (SNS + `check_hold.py`) + 시연 모드
- **무엇을**: 보류함에서 정해진 기간 동안 안 본 사진을 찾아, 목록과 합계 용량을 담은 메일을 SNS로 보낸다. 메일에는 서비스 바로 가기 링크가 들어간다.
- **보류 기간은 설정값**: `.env`의 `HOLD_DAYS=60`. **시연 모드**는 `HOLD_DEMO_MINUTES=2`를 넣으면 기간이 2분으로 바뀌고, 화면 배너(`get_old_hold_photos()`)와 메일이 함께 따라간다.
- **자동 실행**: EC2의 cron이 1분마다 `check_hold.py`를 실행한다.
- **같은 메일 반복 방지**: 알림을 보낸 시각(`notified_at`)을 기록해서 사진마다 한 번만 알린다. 사용자가 "연장"을 누른 뒤 다시 기간이 지나면 그때 다시 알린다.
- **설계 포인트**
  - SNS 메일 제목은 영어(ASCII)만 허용돼서 제목은 영어, 본문은 한글이다.
  - 서버 주소가 계속 바뀌므로, 메일을 보내는 순간 EC2가 자기 현재 주소를 알아내 링크에 넣는다 (인스턴스 메타데이터).
  - 시각은 DB에 UTC로 저장하고, 메일에는 한국 시간으로 보여 준다.
  - 예전에 만든 DB 파일도 지우지 않고 새 열이 자동으로 추가된다 (`init_db`).
- **발표용**: "60일은 기다릴 수 없어서 보류 기간을 설정으로 빼 두었습니다. 시연 모드에서는 2분 뒤 실제로 배너가 뜨고 메일이 옵니다. 1분마다 검사해도 같은 사진으로는 메일을 한 번만 보냅니다."
- 함수: `hold_period`, `hold_period_label`, `get_photos_to_notify`, `mark_notified` (db.py), `build_message`, `site_url` (check_hold.py)

## 3. 예상 질문과 답변

| 질문 | 답변 |
|---|---|
| 버킷이 비공개인데 사진을 어떻게 보여주나요? | Presigned URL로 1시간짜리 임시 접근 권한만 발급합니다. |
| AWS 키가 유출될 위험은? | 코드에 키가 없습니다. EC2는 IAM 역할로 접근합니다. |
| 같은 사진을 또 올리면? | 원본 해시로 비교해 저장하지 않습니다. 단, 재압축본·편집본은 다른 사진으로 봅니다. |
| 왜 HEIC 원본이 아니라 JPG로 저장하나요? | 크롬 등 대부분의 브라우저가 HEIC를 표시하지 못합니다. 호환성을 우선했습니다. |
| 왜 SQLite인가요? | 서버 한 대 규모에 충분하고 별도 비용이 없습니다. 서버를 늘리면 RDS로 옮겨야 합니다. |
| 60일·90일을 시연에서 어떻게 보여주나요? | 보류 기간을 설정값으로 만들어 두어, 시연 때만 2분으로 줄이면 서버가 1분마다 자동 검사해 배너와 메일이 실제로 옵니다. 라이프사이클은 1일짜리 테스트 규칙으로 확인합니다. |
| 왜 t3.micro가 아니라 t3.small인가요? | CPU는 같고 메모리만 1GiB → 2GiB입니다. 사진 변환과 서버 프로그램 여러 개가 동시에 돌아 메모리 여유가 필요했고, 비용 차이는 시간당 약 1센트입니다. |
| B(다른 팀원)도 서버에 접속하나요? | 웹(HTTP)은 누구나 접속할 수 있고, 서버 관리(SSH)는 A의 IP와 열쇠로만 열어 두었습니다. B의 코드는 GitHub를 거쳐 A가 서버에 반영합니다. |
| 1분마다 검사하면 메일이 계속 오지 않나요? | 사진마다 알림 보낸 시각을 기록해서 한 번만 보냅니다. 사용자가 연장한 뒤 다시 기간이 지나면 그때 다시 알립니다. |
| 왜 90일 후에 Glacier IR로 바꾸나요? | 자주 안 보는 사진을 더 싼 저장소로 옮기는 것입니다. Glacier IR은 최소 보관 기간(90일) 요금이 있어 바로 옮기면 손해입니다. |
